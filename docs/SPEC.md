# Gloss — Spec

**Gloss** = **G**raphical **L**ayer **O**ver **S**hell **S**essions
(also: **G**oodbye, **L**ong **O**ff-topic **S**crolling **S**essions)

A *gloss* is a medieval annotation written in the margin beside the specific line it explains — which is what a thread here is.

A desktop GUI for coding agents whose main feature is **threaded replies to individual points** in an agent's response. When the agent returns a multi-point answer (a numbered list of findings, ideas, issues), the user can open a thread on any point, discuss it in a side panel, and come back to the main conversation without scrolling past dozens of turns.

## Core idea: threading is view-only

The agent sees **one linear session**. Threads exist only in the UI.

- Each message is tagged with a `threadId` (`null` = main thread). The UI groups messages by it.
- A message sent from a thread is prefixed with a short tag quoting the anchor, so the agent knows what it refers to. This automates what the user does today by copy-pasting the bullet point.
- The agent's reply is routed to the thread the last prompt came from. Turns are sequential (a message sent during a turn waits in a queue until it ends, or steers the turn from the thread it runs in), so routing is unambiguous.

Consequences, all intended:
- No forking, no merging, no summaries. The agent has everything that happened in every thread in its context.
- One working tree. Edits made from any thread are visible everywhere.
- Works with any agent, because the agent session is not modified.
- The session stays the agent's own: it can be continued in the agent's CLI and back in Gloss (see Shared sessions).

## Anchors (what a thread hangs off)

Anchors live on **agent messages**. Two kinds:

1. **List item** (one click). Every top-level list item in a rendered agent message gets a reply affordance: a Reply button in the item's left margin on hover, and once a thread exists, a reply-count chip after the item's last line. The list stays a list.
2. **Text selection** (fallback). Any text selected in an agent message (prose, code, a list item) can be replied to: right-clicking the selection opens a menu with **Reply to selection** and **Copy**, and `R` replies to it directly. The menu hides shortcut labels. Selecting doesn't show anything by itself. Right-clicking text outside the selection selects its (wrapped) line first, and dragging with the right button held selects every line passed over, including across message blocks; releasing opens the menu. A reply needs text from one agent message: across messages, Reply stays visible but disabled, with a tooltip explaining why, and Copy remains available. The selected span becomes the anchor. The menu has action icons and dividers, avoids the selected text when space allows, and stays inside the window below its title bar. It renders outside clipping panes and closes on resize. Right-clicking into an inactive window releases the composer's focus before selecting, so its caret cannot replace the highlight.

Review sessions add a third kind, on the diff rather than a message: **diff lines** (see Review sessions).

Annotated screenshots add a fourth, on the user's own message: **pins** (see Visual feedback). A pin's thread hangs off the user message the screenshot was sent in.

Anchor positions are stored as offsets into the **source markdown**, not the DOM. Use the markdown renderer's source-position info (e.g. mdast `position` in remark/unified, or `map` in markdown-it) to map the DOM selection back to source offsets. Also store the anchor's text so it can be re-found if offsets drift.

## Wire format

User message in a thread is sent to the agent as:

```
[re: "<anchor text, truncated to ~80 chars>"]
<user's text>
```

Main-thread messages are sent unchanged, except the first one after a thread: when the user's previous message in the session was in a thread, the main message is sent as

```
[re: the main conversation, not the thread above]
<user's text>
```

so the agent doesn't read it as continuing that thread. It takes the thread tag's `[re: …]` form and avoids the bare word "main", which in a coding session reads as the git branch. The UI shows the user's text without the tag; the tag is stored in `wireText`.

A message sent to the main conversation from a thread (see Composer → Send to main) is a main-thread message sent as

```
[re: "<anchor text, truncated to ~80 chars>", continued in the main conversation]
<user's text>
```

so the agent knows which point it answers and that the discussion moves back to the main conversation. Being in the main thread, it ends the thread: the next main message is sent unchanged.

A thread on diff lines in a review session quotes the file and lines instead, with `(old)` for lines on the removed side and a range as `93-95`:

```
[re: src/main/git.ts:93 "<selected text, truncated to ~80 chars>"]
[re: src/main/git.ts:120-124 (old) "<selected text, truncated to ~80 chars>"]
```

A thread on a pin of an annotated screenshot names the pin and quotes its note (without a note, just the pin); with several annotated screenshots in its message, the screenshot's number too:

```
[re: screenshot pin 2 "<note, truncated to ~80 chars>"]
[re: screenshot 2 pin 1]
```

A message with annotated screenshots has their pin lists after its text, in the same text block (so the stored `wireText` is what the agent's replay gives back), then the images:

```
<user's text>

Screenshot with 3 numbered pins:
1: <note>
2: (no note)
3: <note>
```

With several annotated screenshots each list is headed by its number in attachment order, "Screenshot 2 with 1 numbered pin:".

### Agent instructions

Every session gives the agent this text, so it reads the tags as Gloss means them (`AGENT_INSTRUCTIONS` in `src/shared/wire.ts`):

> This session runs in Gloss, a GUI that lets the user reply to individual points of your answers in side threads. You see one conversation; the threads exist only in the UI.
>
> - Every message sent from a thread starts with `[re: "<quote>"]`, quoting the point it's about. Answer about that point and don't bring in other topics, open questions or follow-ups from elsewhere in the conversation; the user raises those in the main conversation.
> - `[re: "<quote>", continued in the main conversation]` replies to that point but moves the discussion back to the main conversation, so answer it in the broader context.
> - Messages in the main conversation are untagged, except the first one after a thread, which starts with `[re: the main conversation, not the thread above]`.
> - A screenshot can come with numbered pins the user placed on it, listed as `1: <note>`. `[re: screenshot pin 2 "<note>"]` is a thread about pin 2.

It is not a message: it goes in each agent's own channel for client instructions, so the transcript and the CLI don't show it. Claude Code: `_meta.systemPrompt.append` on `session/new`, appended to its system prompt. Codex: `_meta.jetbrains.air.customInstructions` on `session/new`, which becomes the thread's developer instructions. Both agents keep what a session was created with: a resume doesn't change it, so sessions created before Gloss sent these instructions go on without them. Gloss sends Claude's on `session/load` too, only so the adapter doesn't take the load for a changed session and restart it.

## Data model

```ts
type Session = {
  id: string
  agentId: string            // which agent config, e.g. 'claude' or 'codex'
  acpSessionId: string       // the ACP session id
  cwd: string                // its project (folder)
  title: string              // renamed in Gloss (titleSet), else the agent's title (session/list), else the first message or folder name
  titleSet?: true            // renamed in Gloss: the agent's title doesn't replace it
  createdAt: number
  model?: string             // model config value picked in Gloss; re-applied on resume
  effort?: string            // effort (thought_level) config value picked in Gloss; re-applied after the model
  mode?: string              // the agent's permission mode (ACP mode id) the session is in; re-applied on resume (see Permission modes)
  autoApprove?: boolean      // agents without a bypass mode: Gloss answers their permission requests itself
  syncedAt?: string          // the agent's updatedAt for this session when Gloss last synced it (see Shared sessions)
  review?: { baseRef: string; headRef?: string }  // a review session (see Review sessions): its base (a commit id, or a branch to take the merge base with, e.g. 'origin/main') and the reviewed commit (a commit id or 'HEAD'; none = the working tree)
  draft?: true               // a review nothing was sent in yet: not listed (see Review sessions → Start)
}

type Pin = { x: number; y: number; note: string } // in the image's pixels; pin n is pins[n - 1]

type Attachment =
  | { kind: 'image'; name: string; mimeType: string; data: string; pins?: Pin[] }    // base64; pins: an annotated screenshot's, drawn into it
  | { kind: 'file'; name: string; path?: string; mimeType?: string; text: string }   // text file

type Message = {
  id: string
  sessionId: string
  seq: number                // position in the linear log — source of truth for order
  role: 'user' | 'agent'
  text: string               // what the user sees (no tag); agent: accumulated markdown
  wireText?: string          // user messages: exactly what was sent
  threadId: string | null    // null = main thread
  acpMessageId?: string      // ACP messageId for agent chunks, when provided
  attachments?: Attachment[] // user messages: images and files sent with it
  steered?: boolean          // user messages: injected into a running turn (see Composer → Steer)
  createdAt?: number         // when it was recorded; missing on messages stored before M9
}

type ToolCall = {             // rendered inline in whichever thread it belongs to
  id: string                 // ACP toolCallId
  sessionId: string
  messageSeq: number         // ordering relative to messages
  threadId: string | null
  title: string
  kind?: string
  status: string             // pending | in_progress | completed | failed | cancelled
  content?: unknown
}

type Plan = {                 // the agent's plan for one turn, rendered as a checklist in its thread
  id: string
  sessionId: string
  seq: number                // where it first appeared in the turn; shares the log's sequence
  threadId: string | null
  entries: { content: string; status: 'pending' | 'in_progress' | 'completed'; priority?: string }[]
}

type Thread = {
  id: string
  sessionId: string
  anchorMessageId: string | null  // the message the anchor lives in (any thread): an agent message, or the user message of a pin; null for line anchors
  anchor:
    | { kind: 'listItem'; path: number[]; text: string }               // [2] = 3rd top-level item
    | { kind: 'selection'; start: number; end: number; text: string }  // source-markdown offsets
    | { kind: 'line'; file: string; side: 'old' | 'new'; start: number; end: number;
        text: string; lines: string[] }                                // diff lines; text = the selection, lines = the full lines
    | { kind: 'pin'; image: number; pin: number; screenshot?: number;
        note: string; text: string }                                   // image = attachment index, pin = its number; text = "Pin 2: <note>"
  finding?: { severity: 'bug' | 'suggestion' | 'nit'; title: string; body: string }  // opened from the agent's findings
  resolvedAt?: number        // review threads: resolved by the user
  createdAt: number
}
```

Projects are folders: those opened with "Open project…" (a `projects` table) plus the folders of existing sessions, matched case-insensitively on Windows.

Notes:
- `anchorMessageId` may point at a message inside a thread. That would allow nested threads later without a migration. Nesting is **not** in scope now.
- A Thread row is created when the user sends the first message on an anchor, not when the panel is opened. A finding's thread is the exception: the agent's findings create it.
- For an agent that shares its sessions (see Shared sessions), messages, tool calls and plans are a cache of the agent's session. Threads, the thread each message belongs to, titles renamed in Gloss, `model`, `effort`, `mode`, `autoApprove`, `steered` and `createdAt` are Gloss's own.
- Open questions and approvals (see Questions and approvals) live in memory only: they belong to a running turn, which doesn't survive a restart.

## Message flow

```
send(text, threadId?):
  if a turn is running in this thread and supports steering: steer(text, threadId); return
  if a turn is running elsewhere or cannot steer: queue.push({text, threadId, attachments}); return   (see Composer → Queue)
  t = threads[threadId]
  wire = t ? `[re: "${truncate(t.anchor.text, 80)}"]\n${text}`
           : lastUserMessage()?.threadId != null ? `[re: the main conversation, not the thread above]\n${text}` : text
  insert Message{role:'user', text, wireText: wire, threadId, seq: next()}
  currentThread = threadId
  { stopReason } = await acp.prompt(sessionId, [{type:'text', text: wire}, ...attachmentBlocks])
  if queue not empty:
    stopReason == 'end_turn' ? send(queue.shift()) : pause the queue

on session/update:
  agent_message_chunk  → append to the current agent Message (group by messageId if present,
                         else one agent Message per turn), threadId = currentThread
  tool_call            → insert ToolCall, threadId = currentThread
  tool_call_update     → update ToolCall
  plan                 → the turn's first plan inserts a Plan, threadId = currentThread;
                         later ones in the same turn replace its entries (each lists the whole plan)
  available_commands_update, usage_update, config_option_update, current_mode_update
                       → the session's live state (status line, slash commands), at any time
  anything else        → ignore

on session/request_permission:
  if Gloss auto-approves for the session (see Permission modes): respond with its allow option
  else show an approval in the running turn's thread and respond with the option the user picks
on elicitation/create (form):
  show a question in the running turn's thread and respond accept (with the form's content), decline or cancel

steer(text, threadId):                                   (see Composer → Steer)
  if no turn is running: send(text, threadId); return
  require threadId == currentThread
  insert Message{role:'user', text, wireText, threadId, steered: true, seq: next()}
  the next agent chunk starts a new agent Message
  outcome = await _session/steering(sessionId, prompt, idleBehavior 'promptRequired')
  outcome == 'promptRequired' → delete that Message; queue it first

cancel():
  answer open questions and approvals 'cancelled'
  notify session/cancel
  pending prompt resolves with stopReason 'cancelled'
```

### Permission modes

Each session runs in one of the agent's session modes (`modes` in the `session/new` and `session/load` responses; Claude Code: Manual, Accept edits, Plan, Auto, Bypass permissions). The mode decides what the agent asks the user before doing.

- **Picker.** The status line's mode item lists the agent's modes; picking one calls `session/set_mode` and saves it on the session (`mode`). A `current_mode_update` from the agent (Claude Code leaving Plan once a plan is approved, say) moves the picker and is saved too. A resumed session is put back in its saved mode.
- **Default mode.** The `permissionMode` setting (global, with a per-project override) says how a session without a saved mode starts, which covers new sessions and ones made before M15. `bypass` (the default): the agent's bypass mode (`bypassModeId` in its config; Claude Code `bypassPermissions`, Codex `agent-full-access`), when it offers it. `agent`: whatever mode the agent starts in (Claude Code's comes from its own settings, Manual unless changed). Either way the mode the session ends up in is saved on it, so changing the setting doesn't move existing sessions. Switching is best effort: if it fails, Gloss logs it, the session stays in the agent's mode, and its requests are shown.
- **Gloss's auto-approval.** For an agent without a bypass mode (OpenCode, custom profiles), the picker also has **Approve requests automatically**, saved on the session (`autoApprove`) and on by default when the setting is `bypass`. An agent with no modes at all gets only that switch. When it is on, and in an agent's bypass mode, Gloss answers each `session/request_permission` itself with the agent's `allow_once` option, or `allow_always` if that is the only allow option (`allow_once` because "always" can make the agent persist a rule); with no allow option, the answer is `cancelled`.

### Questions and approvals

The agent can stop and wait for the user mid-turn. Gloss advertises `clientCapabilities.elicitation.form` (with it the Claude adapter turns on Claude Code's AskUserQuestion tool, and forwards MCP servers' elicitations); URL elicitations aren't advertised, and one that arrives anyway is declined.

- **Where:** a card at the end of the log of the thread whose turn asked (the tool call's thread when the request names a known one), so a question asked while working in a thread appears in that thread. It stays until answered, withdrawn by the agent (`$/cancel_request`), or the turn is cancelled.
- **Approval** (`session/request_permission`, when Gloss doesn't approve it itself): "Approve?" and the tool call's title, the command it will run (from `rawInput.command`), the change it will make (the tool call's `content`, a diff, shown like the tool's details), then one button per option the agent offers, with the agent's names (Claude Code: "Yes", "Yes, allow all edits during this session", "No"). Allow once is the highlighted one; "always" options say in their tooltip that the agent remembers them.
- **Question** (`elicitation/create`, form mode): the message as markdown, then a form built from `requestedSchema`'s properties in order. A string with `enum` or `oneOf` is a single choice (radio cards with each option's title and description; an optional one can be unpicked), an `array` with `items.enum`/`items.anyOf` is a multiple choice (checkboxes), other strings are text inputs (by `format`), `number`/`integer` are number inputs and `boolean` a checkbox. A property's `title` heads it and its `description` is the question. A text field right after a choice that is its "other" answer (the Claude adapter's `<key>_custom`, titled "Other") sits inside that choice as a text box. Other types show as unsupported; a required one can only be declined. **Submit** is enabled once the answer is valid (required fields, choices, lengths, ranges, `pattern`) and sends `accept` with the given fields only. **Decline** is the single dismissal action and sends `decline` (Claude Code tells the model the user skipped). The main process checks the answer against the schema again.
- **Claude's AskUserQuestion** maps to one form: each question is `question_<n>` (its header as title; with several questions, the question text as description and the message "Please answer the following questions."), followed by its optional `question_<n>_custom` "Other" box. Nothing is required, so submitting empty skips. It reaches Gloss in every mode, bypass included.
- **Keyboard:** a card takes focus when it appears, unless the caret is in a field or editor with text in it, or in another card (so it doesn't interrupt typing). While a card has focus, keycap hints show: number keys 1 to 9 press an approval's options in order, or pick a question's choices (toggle for a multiple choice; again unpicks an optional single choice) in the choice that last had focus, else the first; **Enter** approves with allow once, or submits; **Esc** rejects once, or declines. In a text box digits and Enter keep their usual meaning (Enter submits the form), Esc still declines. When an answered card goes away with focus inside, the composer gets it back.
- **Waiting on the user:** the turn is still running (queued messages wait, Stop stays). The status line shows "Waiting for you" (amber), the activity strip says "Waiting for you in …", the session's sidebar row shows an amber pulsing dot instead of the running one, and the thread's header and overview row say "Waiting for you". When the window isn't focused, an OS notification ("Waiting for you: <question>" or "Waiting for your approval: <title>") opens the session and thread on click. Stop answers every open request `cancelled` before cancelling the turn.

Rendering:
- **Main view:** messages and tool calls with `threadId == null`, in `seq` order. Each anchor in an agent message is decorated with its thread's reply count.
- **Thread panel:** a quote of the anchor text, then messages, tool calls and plans with `threadId == t.id` in `seq` order, then a composer. It is one of the side panel's two views (see Conversation view → Side panel).
- While a turn is running, sending from its active thread steers when supported; messages from other threads queue (see Composer → Queue). Show which thread is running.

## Agent integration: ACP

Use the **Agent Client Protocol** (JSON-RPC over stdio) so the app is agent-agnostic. Use the official TypeScript library `@agentclientprotocol/sdk` (check its examples for the current client API; `ClientSideConnection` is deprecated in favor of `client()`).

Lifecycle:
1. Spawn the agent's ACP entrypoint as a child process.
2. `initialize` — advertise no `fs` and no `terminal` client capabilities for v1, so the agent uses its own file and shell tools. Read `agentCapabilities`: `loadSession`, `promptCapabilities` (what attachments it takes) and `sessionCapabilities` (`list`, `delete`).
3. `session/new` with `cwd`, the global `mcpServers` list and the agent's instructions (see Wire format → Agent instructions).
4. Turns via `session/prompt` as above.
5. On app restart: if the agent advertised `loadSession`, use `session/load` to resume, which also syncs the session (see Shared sessions); otherwise preserve displayed history and explain that the user must explicitly create a new conversation. Never silently replace the agent session with lost context.

### Authentication

Agent-agnostic, driven entirely by ACP. No agent-specific login code.

- In `initialize`, advertise `clientCapabilities.auth.terminal: true`. Keep the agent's `authMethods` from the response.
- A request failing with ACP's `auth_required` error (JSON-RPC code `-32000`) during session creation or opening shows a "Sign in" prompt listing the agent's `authMethods` by `name` and `description`. During a turn, the failure ends the turn and offers **Sign in** on its notice instead. Clicking it opens that prompt, then resends the original message after successful sign-in.
- Running a method depends on its kind:
  - **Agent method** (no `type`): call `authenticate({ methodId })`. The agent handles the login.
  - **Terminal method** (`type: 'terminal'`): run the agent's own `command` with the method's `args` appended and its `env` merged in, in a visible system terminal window. The login may be interactive, and Gloss has no embedded terminal. Wait for it to exit.
- After a method succeeds, retry the request that failed. If the agent offers no methods, show the error text.
- If the agent never reports `auth_required`, there is no sign-in UI.

Supported agents: **Claude Code** via `@agentclientprotocol/claude-agent-acp`, **Codex** via `@agentclientprotocol/codex-acp`, and a user-installed **OpenCode v2** native executable via `acp`. Both bundled adapters run on Electron's Node runtime; the Codex adapter includes its native CLI and uses the existing Codex login. Codex's bypass mode is `agent-full-access`. Sign-in, model selection, threading and resume use the same ACP paths; steering is shown only when advertised.

**OpenCode setup:** Settings > Agents contains guided OpenCode setup followed by Custom ACP agents (advanced). OpenCode offers an executable path and **Test connection and save**. Empty discovers a native executable on PATH or OpenCode Desktop's versioned Windows CLI installation. New sessions and the default-agent star are disabled for an unavailable OpenCode installation. Connection tests initialize ACP with a 15-second deadline, reject versions before v2, and create no session or model request. Native `.cmd`, `.bat` and PowerShell wrappers are not launched. Provider setup and model discovery belong to OpenCode, including Ollama; Gloss does not manage model downloads or an inference server. A session retains its agent and working directory, and connection failures never switch it to another agent. Changes to the executable restart idle connections and wait for active turns to finish.

**OpenCode instructions:** a Gloss-owned `opencode-instructions.md` in the data directory carries the thread-routing and diff-tag guidance. Its absolute path is appended to `OPENCODE_CONFIG_CONTENT.instructions`, preserving other inline configuration and native project/user configuration files. Existing inline content must be a JSON object. There are no hidden user turns or edits to project instructions. Model identity must not be inferred from skill descriptions. OpenCode v2's modern terminal auth method runs `acp --login`; unsupported steering queues follow-ups, and subscription usage stays unavailable. Runtime verification and setup details are in `docs/OPENCODE.md`.

**New session** starts a session with the default agent, named on the button. Its ▾ opens a menu: a **Session / Review** switch, then the agents. Clicking an agent starts that kind with it (a review as in Review sessions → Start), so a review can run on another agent without changing the default. The switch keeps the last kind picked. The menu opens with the default agent focused; `Tab` flips the switch, Up and Down move between agents, `Enter` starts. An agent whose plan limit was reported reached (Claude's rate-limit info, kept in memory while Gloss runs) shows "Limit · <reset time>" until the window resets; with nothing known it shows nothing. Each agent has a star; starring one makes it the default (one at a time, saved as `defaultAgent`). Every agent's external sessions are listed, each labelled with its agent. Gloss sessions from both agents remain visible with agent labels; the open session's header identifies its agent. A session keeps its original agent. Gloss-managed MCP servers are shared globally across agents (Settings). Each agent retains its own conversations and context.

**Custom ACP profiles:** Settings > Agents shows compact rows with each agent's name, executable and a neutral Default label. The row opens an editor in place; its action menu holds Remove. Add agent sits beside the section heading. The editor uses standard settings cards, with name, executable and arguments first; Advanced contains the profile ID, instruction variable and environment references. New `custom:<name>` IDs are generated from the name without collisions and can be overridden before saving; existing IDs stay fixed. Edits preserve list order, and returning to the list restores keyboard focus. Test and save initializes ACP with a 15-second deadline and saves only on success. A compact result offers expandable Connection details showing version and advertised resume, discovery, image, embedded-context and steering capabilities. It creates no session or model request. Executables launch directly without a shell; Windows command wrappers are rejected. Settings files can also define `agentProfiles` using the generated schema.

**Custom instruction delivery:** ACP has no standard system-instruction field. A custom agent or wrapper must accept an instruction-file path through a documented argument containing `{instructions}` or the profile's `instructionsEnv` variable. Gloss writes thread-routing and neutral diff-tag instructions in its own data directory. The test verifies ACP, not whether a custom agent reads those instructions. Only the guided OpenCode integration is presented as tested. No project instruction files are modified. Environment references map child variable names to names in Gloss's inherited environment; credentials remain in native stores or inherited variables. Raw custom-agent stderr and protocol error payloads are omitted from diagnostics while ACP error codes are retained for authentication and recovery.

**Profile changes and recovery:** changed or removed profiles disconnect after running turns finish. Conversations keep their profile ID, working directory and history. Removing a profile preserves its conversations, marks it unavailable and asks the user to restore the same ID in Settings > Agents to resume. Removing the default through Settings selects Claude Code as the default. An unavailable saved default is shown as unavailable rather than silently selecting another agent. Agents without session loading retain display history and require a new conversation after restart. Model-server failures never trigger a hosted fallback. See `docs/ACP-PROFILES.md` for setup and verification.

Built-in agent config remains a small table:

```ts
type AgentConfig = { id: string; name: string; command: string; args: string[]; env?: Record<string,string>; bypassModeId?: string }
```

Agents inherit Gloss's environment, so a test run can pick a cheap model with `ANTHROPIC_MODEL=haiku`. There is no dev model setting. Judge the threading UX on the normal model; Haiku produces shorter, less list-heavy answers.

## Settings

- **One `settings.json`** in Gloss's data folder (Electron's `userData`, next to the DB), never in a project. Global settings sit at the top level; per-project settings sit under `projects`, keyed by the folder's absolute path (matched case-insensitively on Windows).
- **A JSON Schema**, `settings.schema.json`, is written next to it on every start, generated from the same field table the app validates against (`src/shared/settings.ts`). A new file's `$schema` points at it, so editors autocomplete and validate, and an agent can read what is allowed.
- **Validation** is owned by the main process. Missing keys take their defaults; unknown keys are ignored and kept.
- **Live reload:** the main process watches the folder (editors often replace the file) and applies changes without a restart. If the file has invalid JSON or values, or is deleted, Gloss keeps the last good settings and shows what is wrong (on the settings screen, and a mark on the sidebar's Settings button). It never resets or overwrites the file because of a bad edit.
- **Settings screen** (the sidebar's Settings button, or `Ctrl+,`; Esc or Done closes it): a list of sections on the left (General, Appearance, MCP servers, Agents, every open project, and Keyboard shortcuts, a read-only list of every shortcut grouped by where it applies, `src/renderer/src/shortcuts.ts`), and one section at a time on the right, under the file's path with "Open in editor" (the system's app for `.json`). Each section is a card of rows: the label and help, then one control (Theme is a three-way segmented control). Changes save immediately: only the changed keys are written, everything else in the file is kept. Agent editors test before saving. Saving is refused while the file isn't valid JSON.
- Each feature adds its own fields when it lands; no field appears before its feature exists.
- **Global MCP servers:** `mcpServers` is one global list shared by all agents in every project. It appears under Global in Settings, even without an open project, with Add, Edit, Remove, Import from Claude and Import from Codex. Every listed server is included; there are no enable/disable toggles. Changes apply on the next turn or resume. Entries use ACP stdio, HTTP or SSE configuration; names must remain unique after Codex replaces Unicode whitespace with underscores. Remote URLs use HTTP or HTTPS. Unsupported transports fail visibly (Codex has no SSE). An attached session reloads using close/load before the next prompt or idle resume; a running prompt finishes first. Agents without close/load need an app restart. Explicit Gloss entries take precedence over same-named native Codex entries; other native extensions remain available. Removing an entry from Gloss does not remove native agent configuration.
- **One-time MCP import:** read Claude user/local configuration (`~/.claude.json`, respecting `CLAUDE_CONFIG_DIR`) and project `.mcp.json` files, or Codex `config.toml` (respecting `CODEX_HOME`) and known project `.codex/config.toml` files. Preview candidates with their source, selection and editable import name before saving. Duplicate names are not selected by default, and conflicts must be resolved before importing. Disabled, invalid or unsupported entries are shown with a reason. Do not execute configured commands, copy OAuth sign-ins, or modify agent files. Resolve supported environment references from the current Gloss environment and copy their values once. Restrictions or working-directory settings that ACP cannot preserve block that entry. Legacy `projects[folder].mcpServers` remain readable and can be explicitly imported into the global list; they are no longer applied per project.
- **Project settings navigation:** each open project has its own entry under Projects, sourced from the project list rather than the settings override keys or active conversation. Selecting one edits that project without changing the current conversation. Projects with no overrides still appear and can be configured without starting a session; only saved overrides need an entry in `settings.json.projects`.
- **Fields so far:** `defaultAgent`: `claude` (default), `codex`, `opencode` or a custom profile ID, the agent New session uses (set with the star in its menu, so the settings screen doesn't list it), `theme`: `system` (default, follows the OS and updates live), `light` or `dark`, `sessionOrder`: `created` (default, newest first) or `activity` (see Projects and sessions), `permissionMode`: `bypass` (default) or `agent`, how sessions without a saved mode start, overridable per project (`inherit` uses the global value; see Permission modes), and `externalEditor`: the command that opens a review's files in your editor, with `{file}` and `{line}` filled in (the path is appended without `{file}`), with a dropdown of editor presets and a Custom command option. Visual Studio Code (`code -g {file}:{line}`) is the default for new settings; existing commands are preserved. Selecting System default app stores an empty command. Presets include VS Code Insiders, Cursor, Windsurf, VSCodium, Zed, Sublime Text, Notepad++, Notepad and Kate. Custom commands remain editable as text, and the picker follows file edits live. `captureShortcut`: the key combination that starts a capture, in Gloss or any app (see Visual feedback), `Ctrl+Shift+PrintScreen` by default, empty for none. The settings screen records it in one field, the width of the other settings' controls, showing the keys as keycaps ("None" when empty): click it ("Press keys…") and press the keys; held modifiers show as they are pressed; Backspace or Delete clears it; Esc keeps the old one. The current shortcut is paused meanwhile so the keys reach the field, and PrintScreen is read from its keyup, the only event Windows sends. The keys are written as an Electron accelerator with the modifiers in a fixed order (`Ctrl+Alt+Shift+Super+<key>`); a key that would stop typing (a letter or digit without Ctrl, Alt or the Windows/Command key) is refused with a short hint under the field ("Add Ctrl, Alt or Win."); F1 to F24 and PrintScreen may stand alone. No buttons and no tooltip beyond the description. A value typed into settings.json is checked the same way. When another app already holds the keys, the field says so under it. On Windows it runs through `cmd.exe` (editors are often `.cmd` launchers), so a path containing `%` or `"` is refused. The renderer sets `data-theme` on the document, and main sets Electron's `nativeTheme.themeSource` to the setting, so native parts (the window controls' hover, dialogs) match it.

## Stack

- **Electron**, built with `electron-vite`, TypeScript throughout.
- **Main process** owns everything agent-related: spawning, the ACP connection, persistence. Exposes a narrow IPC API to the renderer:
  - `projects.list() / projects.open() / projects.agentSessions(path, agentId)`
  - `sessions.list() / sessions.create(cwd, agentId) / sessions.import(cwd, agentId, acpSessionId, title) / sessions.open(id) / sessions.rename(id, title) / sessions.delete(id) / sessions.setModel(id, value) / sessions.copyMarkdown(id, threadId) / sessions.saveMarkdown(id, threadId)`
  - `send(sessionId, text, threadId | null, attachments, fromThread?)` (queues while a turn runs; `fromThread`: Send to main), `steer(sessionId, text, threadId | null, attachments)`, `cancel(sessionId)`, `queue.edit(sessionId, id, text) / queue.remove(sessionId, id) / queue.resume(sessionId)`
  - `git.status(cwd)`
  - `threads.create(sessionId, anchorMessageId, anchor)`
  - `capture.start()`: the region overlay (see Visual feedback); resolves to the picked PNG or null
  - `history()`: the user's sent messages for the composers' Up and Down
  - `sessions.open` returns the session's messages, tool calls, plans and threads
  - `settings.get() / settings.update(patch) / settings.openFile()`
  - an event stream: message/tool-call/plan upserts, turn start/end, session upserts and deletes, live session state, queue changes, notification clicks, settings changes
- **Renderer** only renders. Framework is the implementer's choice (React is fine).
- **No menu bar** on Windows and Linux (`Menu.setApplicationMenu(null)`). The default menu's zoom shortcuts (`Ctrl+=`, `Ctrl+-`, `Ctrl+0`) are kept, plus DevTools (`F12`, `Ctrl+Shift+I`) and reload (`Ctrl+R`) in development. `F11` toggles full screen: a borderless window over the whole monitor (taskbar included, not exclusive, so Alt+Tab and notifications still work). Entering it shows "Press F11 to exit full screen" for a few seconds; `Esc` doesn't leave it (it closes menus and dialogs), and it isn't remembered across restarts. On macOS the system's own full screen (green button, `Ctrl+Cmd+F`) applies. macOS keeps the default menu: it lives in the system menu bar, and copy and paste need its Edit menu.
- **Title bar:** drawn by the app (`titleBarStyle: 'hidden'`), a 40px strip across the top of the window in the frame's color (`--title-bar`, the same as the sidebar's), that drags the window. It shows the bead and the `gloss` wordmark (`docs/BRAND.md`) at its start, over the sidebar. The system's window controls sit over its end (`titleBarOverlay` on Windows and Linux, in the title bar's color and the theme's ink and updated when the theme changes; the traffic lights over its start on macOS), and the layout keeps clear of them with the `titlebar-area-*` CSS variables. The window title stays "Gloss" (taskbar, Alt+Tab).
- **Security:** agent output is untrusted (it can contain text from files and web pages). `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, expose only the IPC API via `contextBridge`, and **sanitize rendered markdown** (no raw HTML, safe link handling: open external links in the system browser).
  - Markdown links to absolute local files (Windows drive paths, slash-prefixed drive paths, POSIX paths, or local `file:///` URLs) open through the main process in the configured External editor. HTML files (`.html` or `.htm`, case-insensitive) instead open externally through their local file URL for browser previews. Optional `:line`, `:line:column`, and `#Lline` suffixes select the line in the editor; columns are ignored. Without an editor configured, reveal non-HTML files in their folder. Validate the destination again in the main process and require an existing regular file. Never navigate the renderer to a file, launch non-HTML files through their default application, or accept network paths. Relative links remain plain text; failures appear next to the link.
- **Persistence:** SQLite. Prefer the built-in `node:sqlite` if the Electron version's Node supports it; otherwise `better-sqlite3` with `electron-rebuild`.
- Target platform: Windows first (the developer's machine); don't do anything that prevents macOS/Linux.

## Projects and sessions

The sidebar (`docs/mocks/target.html`) shows one project at a time:

- **Project switcher** at the top: the current project's name and where its folder is (the parent folder, the home folder shortened to ~; the full path in its tooltip). Its menu lists every project by name, alphabetically, so the order doesn't change with use (state dots with hover labels mark Working and Waiting, and unseen Completed or Failed turns, including on the selected project; concurrent work and unseen outcomes can both show) and "Open project…", a folder picker that adds a project. Hovering a project in the menu shows a small **×** that deletes it.
- **Delete project** asks for confirmation, then deletes each of the project's sessions that were opened in Gloss as below (the agent's copies too) and removes the project. The agent's sessions that were never opened in Gloss are kept, and the folder's files are not touched.
- **+ New session** starts a session in the current project (`Ctrl+N`). Without a project it opens the folder picker.
- **Sessions:** one list of the project's sessions, newest first, or most recent activity first with the `sessionOrder` setting (a Gloss session by its newest message), each row with one lead slot (a running dot while a turn runs, else a red dot when its last turn failed, or a green one when it finished, while the user wasn't looking (another session open, or Gloss in the background), until it is looked at (opened, or open when Gloss comes to the front) or runs again, else the review icon for a review session, or a hollow ring for the agent's own sessions not opened in Gloss), the title over the agent's name (and a review's open thread count), and the age it is sorted by; the current session has a pink bar. ACP doesn't say when the agent's own sessions began, so those go by their `updatedAt`, and one opened in Gloss keeps that time as its creation, so it keeps its place: those opened in Gloss and, when the agent advertises `sessionCapabilities.list`, the agent's own sessions for the folder from `session/list` with `cwd` (for example ones started in the `claude` CLI). Right-clicking a session, or its **…** button (shown on hover, in place of the age), opens its menu: Rename, Open in new window, Copy as markdown, Save as markdown…, Delete…. A session open in its own window shows a window icon after its title (see Session windows). Double-click (or F2) renames in place.
- **Opening an agent session Gloss has no record of** creates its record, and the `session/load` replay builds its log: `user_message_chunk` and `agent_message_chunk` become messages (split by `messageId`, and at tool calls), `tool_call`/`tool_call_update` become tool calls, user messages are placed in threads as in Shared sessions. If the load fails, the half-made record is removed.
- **Delete** happens at once (no confirmation), cancels a running turn, calls `session/delete` when the agent advertises `sessionCapabilities.delete` (Claude Code then removes its transcript under `~/.claude/projects`), and removes the session, its messages, tool calls and threads from the DB. If the agent's delete fails, the Gloss copy is still removed and the sidebar says so (unless the session never had a message: Claude Code writes no transcript until the first prompt, so there is nothing to lose).
- **Opening a session resumes it on the agent** in the background (`session/load`), so its model, commands and usage are known before the first message, and syncs it.

## Shared sessions

When the agent advertises `loadSession` (Claude Code does), the agent's own copy of a session is the source of truth for the conversation, and the same session can be continued in Gloss and in the agent's CLI (`claude --resume`), one at a time. Noticing changes made elsewhere also takes `sessionCapabilities.list` and `close`.

- **What lives where.** The agent's session (Claude Code: its transcript under `~/.claude/projects`) decides which messages, tool calls and plans exist and in what order. Gloss's DB caches them for display and search, and adds what a linear session can't hold (see Data model → Notes).
- **Sync.** Each `session/load` replay is matched against the cached log, in order: agent messages by `messageId` (the Claude adapter uses the same ids live and in the replay), user messages by their wire text, tool calls by `toolCallId`. A matched entry keeps its Gloss id, thread and fields, so thread anchors stay valid. An entry the cache doesn't have (sent from elsewhere) is added where the replay has it. A cached entry the agent's session no longer has (a rewound turn, a prompt that never reached the agent) is removed, with the threads anchored on it. Two exceptions:
  - Cached entries before the first one the replay shares are kept: after a compaction, Claude Code's replay starts at its summary, so the replay is no longer the whole history.
  - Plans are kept. The replay's plans are recorded only for turns the cache doesn't have.
- **Claude Code's own messages** are skipped: the summary that starts the history after a compaction ("This session is being continued from a previous conversation…") and the marker of a cancelled turn (`[Request interrupted by user]`). The text of a cancelled turn's answer is taken from the replay, which has more of it than Gloss saw.
- **Messages from elsewhere** are placed by their tag: `[re: "<text>", continued in the main conversation]` for a thread of the session goes to the main thread; `[re: "<text>"]` goes to the thread whose own tag is that line (the most recently active if several match); `[re: the main conversation, not the thread above]` and untagged messages go to the main thread. A tag that matches no thread stays in the text and the message goes to the main thread. The agent's output goes to the thread of the user message before it. Images come back as image chunks; text files come back as text (`[@name](uri)`, then `<context ref="uri">…</context>`) and show as file attachments again. Such messages take the agent's `updatedAt` from before the load as their `createdAt`.
- **When Gloss syncs:** when a session is resumed, and, for a session already running on the agent, when it is opened, when the window regains focus with it open, and before a prompt or queued message is sent. Gloss compares the agent's `updatedAt` for the session (from `session/list`) with `syncedAt`, and reloads the session if it moved: `session/close`, then `session/load`. The close is required: a `session/load` of a session the adapter already holds replays the new history but keeps the running process, whose model doesn't see it. Never while a turn runs; before a send, the turn's own message waits at the end of the log until it goes out. A load changes `updatedAt` itself, and so does each turn, so `syncedAt` is recorded after both. An agent without `session/list` or `session/close` syncs only when resumed.
- **Deleted outside Gloss.** If `session/load` fails because the agent no longer has the session (ACP `resource_not_found`), Gloss deletes it too (messages, threads, queue) and the sidebar says so in a neutral note above the session list, dismissed with its ×. Errors from sidebar actions (creating, importing, deleting) show in the same place, in the failed color. A session that never had a message is the exception: Claude Code writes no transcript until the first prompt, so it gets a new agent session in its place. Missing from `session/list` alone is not enough (the list is paged). Other load failures show the error and are retried on the next open or send; Gloss doesn't start a new agent session in place of one it couldn't load.
- **In the CLI,** messages sent from threads show with their tags, and the threads are flattened into one conversation, which is how the agent sees them anyway.
- **One at a time.** Gloss can't tell when the CLI is using a session. Using it in both at once gives the transcript two writers (Claude Code then branches it), and the next sync shows the branch the agent loads.
- Agents without `loadSession` keep the DB as the display state.

## Conversation view

- **Layout:** the log, composer and status line share one centered column that grows with the pane (820px up to 1080px), and the conversation text grows from 15px to 16px and 17px on wide panes (markdown sizes are relative to it). The thread panel grows with the window too (420px up to 600px). The sidebar and the thread panel can be resized by dragging their inner edge, or by focusing that edge and pressing the arrow keys; double-click resets it. **«** beside the project switcher at the top of the sidebar collapses it to a thin rail like the side panel's (a sessions button that expands it (the project's session count in its tooltip); running sessions show on their rows, the project switcher and the taskbar icon, not on the rail); the collapsed state is remembered like the widths. The sidebar stays between 180px and 480px (at most 40% of the window), the thread panel at least 320px while leaving the conversation 360px. Widths are UI state, remembered in the renderer's localStorage, not settings. In a narrow window the panes make room for the conversation's 360px: the thread panel narrows first (down to 320px), then the sidebar (down to 180px). If both are open and that is still not enough, the one opened earlier shows as its rail until the window is wide enough again (this doesn't change the remembered collapsed state); expanding that rail keeps it open and collapses the other instead. The window itself never scrolls; only its panes do. A conversation or thread scrollbar spans the message log and pinned footer (composer and status line), and its thumb hides when idle unless hovered. When a log's pane changes height (the composer grows or shrinks a line), the log keeps its distance from the bottom, so the text above the composer moves with it instead of going under it. Collapsing the sidebar leaves its expand button where the collapse button was.
- **Side panel** (`docs/mocks/target.html#overview`): the right-hand panel is collapsible and shows one of two views.
  - **Collapsed**, it is a thin rail with a threads button, whose tooltip gives the session's thread count (in a review session, its open line threads plus one for the general conversation, which the panel also holds). Clicking it opens the overview. `Ctrl+Shift+T` toggles the panel.
  - **Threads overview:** two tabs, **Threads** and **Queue**, each with its count.
  - **Threads tab:** the session's threads, oldest first. Each row shows its quote (two lines at most), the reply count, the last activity ("5m ago", from its newest message, or the thread's creation for messages stored before M9) "working" while the turn runs there, "queued" ("2 queued") while messages wait to run there, and "paused" when the queue is paused. Clicking a row opens that thread. With no threads, it says how to start one.
  - **Queue tab** (`Ctrl+Shift+Q`): a timeline of the session's messages, each under the name of the thread it runs in ("Main conversation" for the main one). On top, the queued messages, the next one at the bottom, with Edit and Remove as above the composer, and "paused" with **Resume** when the queue is paused; clicking one opens its thread, or focuses the main composer. Below, every message sent in the session (from the log, so after a restart too), newest first, with when it was sent. Each row has a state dot: queued or paused for the waiting ones; working (the running turn's message, also highlighted), completed, cancelled or failed for the sent ones, from its turn outcome (none for turns Gloss didn't run). The turn in progress thus moves up the list. The tab opens scrolled to the line between the two. Clicking a sent message opens its thread (or stays on the main conversation), scrolls to it and highlights it briefly. The thread view's back button then reads **← Queue** and returns here.
  - **Thread names:** a thread is named by the start of what it replies to (the list item's or selection's text, cut to 40 characters), e.g. in the activity strip and the Queue tab. The thread view's header doesn't repeat it, as the quote sits right below.
  - **Thread view:** the thread panel, with **← All threads** to go back to the overview. Reply badges, anchors in the conversation, the status line and notifications open a thread straight into this view, expanding the panel if needed.
  - The panel icon at the header's end (or `Ctrl+Shift+T`) collapses the panel from either view; `Esc` doesn't. Each session remembers the thread its panel showed, so expanding the panel, or coming back to the session, shows it again (while Gloss runs). It always starts collapsed when Gloss launches. Expanded, it uses the thread panel's width and resize handle; the rail has a fixed width.
- **Plans:** an agent's `plan` updates render as a checklist (pending, in progress, done, with "2 of 4 done") in the thread whose turn produced them, at the point the plan first appeared, and update in place as the agent works. A plan is stored, so it survives a restart. Each turn that reports a plan gets its own checklist; an earlier turn's checklist keeps its last state. Claude Code reports its todo list this way; it only gives older models its todo tools by default, so Gloss sets `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` in the Claude agent's environment. A sync records the plans in the replay too, one per user message.
- **Activity strip:** above the main composer once a turn has run: where the agent works (a thread or the main conversation), or where the latest turn ran and its outcome, and queued messages. It is one raised bar; its main part names the place with a state dot: "Working in “thread name”" (or "Working in main conversation") while a turn runs there, then "Done in", "Cancelled in" or "Failed in" from that turn's outcome ("Last worked in", grey, without one). It shows also while the side panel shows that thread. Clicking it opens the thread, or for the main conversation scrolls the log to the bottom and focuses the main composer. "2 queued" sits at its right end and opens the Queue tab (the status line then doesn't repeat it). With neither there is no strip.
- **Turn outcomes:** when a turn ends, the user messages sent in it (the one that started it and any steered in) record how: `completed` (`end_turn`), `cancelled`, or `failed` (an error, or a turn cut short: max tokens, refusal). Stored in the DB (`messages.outcome`), so they survive restarts and syncs that keep the message.
- **Turn notes:** when a turn ends other than normally, a note follows it in the log of the thread it ran in. A failed turn's note is a box in the failed color with an alert icon and the error ("The turn failed: …"); a cancelled turn gets a small grey line ("Cancelled."). A cut-short turn gets a failed notice ("The agent stopped: max tokens."). Failed notices offer **Sign in** for ACP `auth_required`, otherwise **Retry**. Retrying resends the original prompt, with its original thread, attachments and wire context. While recovery is pending its button is disabled; dismissing sign-in or a recovery error leaves it available again with an explanation. A failed retry gets its own notice. Notes and recovery actions are kept only while Gloss runs.
- **State colors:** one color per state everywhere a turn, message or step shows one (`--state-*` in the stylesheet): working blue (pulsing dots, running tool calls, plan steps in progress), completed green (tool calls, plan steps, turn outcomes), queued yellow, paused purple, failed or cancelled red. Not used for things that mean something else: PR badges follow GitHub's colors, and warnings (a rate limit near, a full context) stay amber.
- **Header:** the session title and the agent name, and at its end **Pop out** (see Session windows). A session is exported from its sidebar menu; the thread panel's header has icon buttons to **Find in main session** (scrolls the main conversation to the thread's anchor and highlights it; not in review sessions, whose conversation that panel replaces) and to **Export** one thread.
- **Export format:** `# Title`, then each message as `**You**` / `**Agent**` and its text, tool calls as `_Tool: title (status)_`, attachments named; for a whole session, each thread with replies follows under `## Thread: “anchor”` with the anchor quoted.
- **Tool calls** of a turn that follow each other share one box, a row each: an icon for the ACP tool kind, the title (a command's in monospace), and a check when done, a pulsing dot while it runs (the agent reports a command it is executing as `pending` too) or "failed". Internal steps the user can't act on (Claude Code's `ToolSearch`) fold into a "Show 1 internal step" line. Rows are collapsed. Clicking expands what the agent did, from the tool call's ACP `content`: a command's full text and its output (the Claude adapter sends output as a console code block when the client has no terminal capability), a file edit (`diff` content) as a unified line diff with unchanged stretches collapsed to 3 lines of context, other content as markdown.
- **Code blocks** are highlighted with Shiki (JavaScript regex engine, no WebAssembly, themes `github-light` and `github-dark` as `light-dark()` colors, so they follow the theme). Common languages load at startup, others the first time they are seen; until then the block renders plain and re-renders when ready. Highlighting splits the same source-offset spans selection anchors use, so anchors in code keep working. Each block has a Copy button.

## Review sessions

A session for checking an agent's work (`docs/mocks/target.html#review`). The center shows the diff of the branch, threads hang off its lines, and the agent reviews it when asked. To the agent it is still one linear session, separate from the session that wrote the code, so the review starts with clean context.

- **Start:** **Review** in the **New session** ▾ menu opens a review with the agent picked there, and `Ctrl+Shift+D` one with the default agent (pressed again in the open review, it goes back to the view before it, bringing back the sidebar if opening the review collapsed it); neither sends anything: the diff is there to read, the agent session starts in the background (so the status line works), and the agent waits for a question, a line reply or **Run review**. Until something is sent the review is a **draft**: it isn't in the session list, and the project keeps one, so starting a review with the same agent shows it again (range, panels and all; another agent replaces it) until something is sent in it, a new review replaces it, or Gloss restarts, which drops it. The first message sent lists it. Whatever is sent first, the agent is told the range in a first line only it sees (as when the range changes). A new review (this or **New review**) opens with only the diff: the sidebar collapsed to its rail, the side panel collapsed (it opens on the general conversation, where a review runs) and the file list hidden. From then on each keeps the state it is set to. The session list shows it with a review icon, titled "Review: #N <PR title>" when the branch has an open pull request, else "Review: <branch>", with a count of its open threads. **New review** in a listed review's header opens a fresh draft of the same range with the same agent (a new agent session); the old one stays in the sidebar with its threads.
- **What is reviewed:** the diff from a **Base** to a **Review** commit, picked in two dropdowns in the header (`Base: merge base with origin/main · 3c3c5f9 ▾ → Review: working tree ▾`) and stored as `review.baseRef` and `review.headRef`.
  - **Review** is **Working tree, including uncommitted** (the default: staged, unstaged and new files, so the agent's fixes show up), **HEAD**, or one of the branch's recent commits. The diff is `git diff <base>` plus untracked files as new files for the working tree, else `git diff <base> <commit>`.
  - **Base** is the **merge base with** a branch (recomputed at each refresh), or a commit (used as is). The dropdown offers the merge base with the default branch, with the open pull request's base branch and with the session's own base branch, then the commits. Each dropdown tags its default entry **default**, and **Reset** beside them, shown while the range differs, goes back to the default base and the working tree.
  - **Default base:** the merge base with the open (or draft) pull request's base branch, `origin/<base>` (fetched when the review starts; the local branch if there is no such remote branch), found with `gh`. Without one, the merge base with the default branch: `origin/HEAD`, else `origin/main`, `origin/master`, `main` or `master` (the remote's first: a local `main` that is never pulled falls behind as pull requests merge on GitHub), fetched when the review starts if it is a remote branch. On the default branch itself the merge base is `HEAD`, so the review shows uncommitted changes.
  - **Commits** listed are the branch's (first parents of `HEAD`), newest first: those since the merge base with the default branch and 20 more, at most 50, with a filter box. The lists refresh when a dropdown opens. A commit's short hash links to its page on GitHub when `origin` is a GitHub remote.
  - **Changing the range** re-reads the diff; threads follow their lines or are marked outdated, as after an edit. The agent is told at the start of the next message sent to it, in a first line only it sees: `[The diff under review is now git diff <base> <commit>.]`.
  - With nothing to review the diff says so. The header also shows file and line counts. The main process reads the diff; the renderer gets it through the preload API.
- **Refresh:** the diff is re-read when the session opens, when the window regains focus with it open, after each tool call that completes and at the end of each turn, so the agent's fixes show up as it makes them.
- **Diff view:** one scroll with every file stacked flush, each under a sticky header (path, "new", *committed*, *uncommitted* or *committed + uncommitted*, two icon buttons with tooltips, **Show in File Explorer** (Reveal in Finder on macOS, Show in folder on Linux) and **Open in external editor** (at the file's first added line, with the `externalEditor` setting), absent for deleted files, then `+` and `−` counts); clicking anywhere else on the header collapses or expands the file, and **Collapse all** / **Expand all** in the review header does every file. The review header's tools are icon buttons with tooltips, in this order: the file list, Collapse/Expand all, Split/Unified, Comments, the open-thread count with its stacked previous/next buttons, then, past a divider, Run review, New review (not in a draft) and Pop out (see Session windows). Binary files show as a header only. Every file starts collapsed, so a large review opens fast; clicking a file in the file tree or opening a thread on its lines expands it. Rows render in blocks of 150 lines that the browser skips while they are off screen (`content-visibility: auto`), so large diffs stay usable. Code is highlighted with the conversation's Shiki setup.
  - **Split or Unified** (two icon buttons), side by side by default. In split view lines don't wrap: each side scrolls sideways on its own, with its scrollbar pinned to the bottom of the view while the file is on screen, and Shift+wheel or a horizontal trackpad scroll over a side moves that side. Below 640 px of diff width, split shows as unified.
  - **More of the file:** each hunk header has buttons that show the unchanged lines hidden around it, in one small widget at the right of each hunk header: two stacked half-height buttons, an up chevron for 10 more lines at the top of the gap, under the previous hunk (from the top of the file before the first), over a down chevron for 10 more at its bottom, over the hunk (up from the end of the file after the last), and beside them an up-and-down chevron for the whole gap; a gap fully shown merges the hunks. **Entire file** (an icon button with a tooltip, beside the open buttons in a modified file's header; highlighted while on) shows every line. The lines come from the file at the reviewed commit (the working tree's file when that is reviewed), read by the main process when first asked for and re-read with the diff. They take threads like the diff's lines (see Line anchors).
  - **File tree:** a collapsible column listing the files (name, folder, counts, open threads) that highlights the file in view and jumps to a file when clicked. Right-clicking a file (not a deleted one) opens a menu with the header's **Show in File Explorer** and **Open in external editor**.
  - Split or unified, the tree's visibility and comment visibility are UI state in the renderer's localStorage.
- **Line anchors:** code selected in the diff, including unchanged lines shown around the hunks, can be replied to as in a message. The anchor records the file, the side (old or new), the line range, the selected text and the full text of those lines. A thread on unchanged lines keeps them shown (from the nearer end of their gap, with 3 lines around them) and re-finds them like any thread, so files with threads are read when the review opens. In split view a selection stays on the side it started on. In unified view a selection that covers both removed and added lines anchors to the new side's lines. A new thread's panel shows the tag it will be sent with (see Wire format).
  - **Right-clicking a selection** opens a menu with **Reply to selection**, **Copy** and **Open in external editor**, which opens the file at the selection's first line (a removed line opens at the line that now follows where it was; absent for deleted files). It uses the conversation menu's icons, dividers and placement, without visible shortcut labels. Right-clicking a line of code outside the selection selects that line, and dragging with the right button held selects every line passed over (in that file, and in split view on that side); releasing opens the same menu on them (not on a blank line). Left-drag also stays in its starting file: other files become unselectable before native selection begins, avoiding a flickering highlight. Hunk headers (`@@ ... @@`) are not selectable. A selection without a valid line anchor can still be copied.
- **Comment cards:** each thread shows as a card under its last line, on its own side in split view: severity, title, two lines of the finding, reply count, last activity, and "working", **Outdated** or **Resolved**. A thread the user started has no severity ("yours") and is titled by its first message. A colored marker in the gutter at the thread's first line stays when the card is hidden. Cards start expanded; **▴** collapses one to its marker, and clicking a marker expands it again. **Comments** (a speech-bubble toggle) in the header (`Ctrl+Shift+H`) hides every card at once. Clicking a card or marker opens its thread in the side panel and highlights its lines.
- **Run review:** an icon button in the review header, and a button in the empty general conversation ("Ask about the change, or have the agent review it."), disabled while a turn runs. It sends a message that asks the agent to review the diff against the base commit (it reads the diff itself) and to answer with a short summary and a fenced `gloss-findings` block: a JSON list of `{ file, side, start, end, severity, title, body }`, and opens the general conversation. It can be run again, after fixes or a range change. When a turn in the general conversation ends, Gloss opens one thread per finding listed in it, at its lines, with the finding stored on the thread (`finding`); findings that already have a thread open nothing new. The block shows in the general conversation as a row ("7 findings") instead of JSON. A finding whose lines aren't in the diff is listed there as text. The message Gloss sent shows as a line in the general conversation ("You ran a review"), not as a user message.
- **Fixes:** the review agent changes files itself when asked in a thread. Its edits appear in the diff at the next refresh.
- **Outdated threads:** at each refresh a thread re-finds its lines by their text on the same side of its file, nearest the old position, and moves with them. When they are gone the thread is **Outdated**: its card stays near where the lines were and shows them struck through. A thread whose file left the diff stays under that file's header, marked "no longer changed". Outdated threads still take replies.
- **Resolve:** a thread has **Resolve** (then **Reopen**) in its header. Resolved threads collapse to a grey marker, dim, and are hidden by the overview's Open filter.
- **Side panel:** the overview starts with a pinned **General conversation** card (the latest agent message, the message count) that opens the main thread in the panel with **← All threads** and the main composer. Below it, the threads grouped by file in diff order and sorted by line, each with its marker, lines, title, severity, replies, last activity and state. Filters: **Open** (default), **Resolved** or **All**, with counts, and a **kinds** menu that checks which kinds are shown (all by default). The thread view adds the severity, `file:lines` and **Resolve** to the header, and quotes the lines with their numbers (struck through when outdated) above the finding's title and the messages. The Queue tab is unchanged.
- **Navigation:** `N` and `P` (outside text fields), or the stacked up and down buttons in the header after "2 of 7 open", go to the next or previous open thread in file and line order: the diff scrolls to it, its card expands if comments are shown, and it opens in the side panel.
- **Export:** a review session exports like any session; each line thread is headed `## Thread: src/main/git.ts:93 “<text>”`.
- **Agent instructions:** a review session's instructions add that `[re: path:line "…"]` tags refer to the diff under review and that the `(old)` side is the base's version, and describe the `gloss-findings` block for when the user asks in the general conversation for a review or for problems, so those findings open threads too.

## Session windows

Any session, a conversation or a review, can be popped out into its own window, so the main window stays free to show other sessions (for example, reading them while a review's diff stays open).

- **Pop out:** an icon button with a tooltip at the end of the session header (in a review, after New review past the divider; drafts have it too), **Open in new window** in a session row's menu, or `Ctrl+Shift+O`. The session opens alone in a new window: its center (the conversation, or the review's diff), side panel, composer and status line, with no sidebar or settings. Its open thread, side panel state, unsent drafts, where its conversation, threads and diff are scrolled (kept by the paragraph or diff line at the top, so it holds at another width) and, for a review, its range, file list and collapsed files come along. The main window goes back to the view visited before it (as Back would), or to the project's empty state without one.
- **One place at a time:** a session is open in either the main window or its own window. Opening a popped-out session from anywhere (the sidebar, search, a notification, starting a review that reopens a popped-out draft) brings its window to the front instead. Back/Forward and `Ctrl+Tab` in the main window skip popped-out sessions, as they skip deleted ones. Several sessions can each have a window.
- **Sidebar:** a popped-out session's row shows a small window icon after its title; clicking the row brings its window forward. Its menu works as usual. Deleting the session closes its window.
- **Return to main window:** in the popped-out window's header, in Pop out's place, with the same icon flipped (or `Ctrl+Shift+O` there). It closes the window and opens the session in the main window, with the same state it took along; the main window's previous view goes on the Back history, and the main window comes to the front. Closing the window with its own close button only closes it: the session doesn't open in the main window.
- **Shortcuts in a session window:** the session's own work there (`Ctrl+L`, `Ctrl+J`, `Ctrl+Shift+T`, `Ctrl+Shift+Q`, `Ctrl+Shift+H`, `N` / `P`, `Esc`, zoom, F11). `Ctrl+Shift+F`, `Ctrl+N`, `Ctrl+Shift+D`, `Ctrl+Tab` and `Ctrl+,` bring the main window forward and act there, except that `Ctrl+Shift+D` in a review's window closes it. The capture shortcut goes to the composer used last, in whichever window. **Find in main session** acts in the window that holds the session.
- **Drafts:** a popped-out draft is listed by its first message, as in the main window. Closing its window keeps the draft, as leaving it does; starting a review with its agent then opens it in the main window.
- **Restart:** nothing reopens. Gloss keeps only the size and position of the last session window moved, resized or closed, and opens a new one there (offset from a window already in that spot); if that spot is off screen, it opens at the default size centered on the main window's display.
- **Closing the main window** quits Gloss, session windows included. Closing or quitting while any session is working first asks for confirmation in a themed Gloss dialog in the focused window, with Keep open focused by default; dismissing leaves every session running.
- **Implementation:** a session window loads the main window's page and preload with the session in its URL (`index.html?session=<id>`), with the same security settings, window-open handler and navigation guard. Main sends every event to every window, and its own record of which session each window holds (sent to the renderers as it changes) drives the sidebar's icon and the skipping above. Dialogs open over the window that asked. The main window's renderer still owns the taskbar badge, unseen dots and chime, so nothing plays twice; a focused session window counts as looking at its session.

## Search

- **Search conversations** in the sidebar, or `Ctrl+Shift+F` (`Cmd+Shift+F` on macOS), opens a dialog from anywhere, including settings. Escape or clicking outside closes it; focus stays inside while open and returns on close. The dialog is anchored 32 px from the top of the window; results grow and scroll below the input, keeping it stationary as matches arrive. Search leaves the conversation and running turns in place.
- Search includes all history cached in Gloss: user and agent messages in the main conversation and threads, plus tool titles, textual output and file diffs. Agent sessions that have only been listed become searchable when opened and loaded. Attachments and image payloads are not indexed.
- Choose **Everything**, **Current project** or **Current session**, and filter by **Your messages**, **Agent messages** or **Tool output**. Unavailable scopes are disabled. Words match together in any order; double quotes match a phrase. Search input is literal, with no FTS operators. Search waits 150 ms after input changes and discards superseded responses.
- Results are grouped by session (its title and folder once per group, in the order of the best match), each showing who wrote it (You, Agent, Tool output), where (the thread's quote, or Main conversation) and a highlighted excerpt that shows inline code as code. Results are ordered by relevance, up to 100; the dialog says when more matches exist and suggests refining the query. Loading, empty results and errors are shown explicitly. The arrow keys in the search field move a highlight through the results and Enter opens it; results are reachable with Tab and Enter too.
- Opening a result selects its session, opens its thread if needed, scrolls to the entry and highlights it briefly. Tool results expand their details. A result deleted meanwhile reports an error.
- SQLite FTS5 indexes are maintained in the main process by insert, update and delete triggers, including streaming text, replay syncs, clears and cascading session deletions. An append-only schema migration indexes existing history. The renderer searches through a typed preload IPC call; excerpts are never rendered as HTML.

## Composer

- **Slash commands:** typing `/` at the start offers the agent's `available_commands_update` list (name, argument hint, description), filtered by prefix. Arrow keys move, Enter or Tab completes, Escape dismisses. Enter on an exact match sends it. Gloss adds `/clear`, which it runs itself: the session gets a fresh agent session in place, keeping its title, and the old one is deleted (the agent's copy too, with the session's messages, threads and queue). Refused while a turn runs.
- **Stop:** only the composer of the thread the turn runs in has **Stop**; `Esc` in it does the same unless the slash commands are open. Other composers can only queue. A cancel stops that turn alone: the queue moves on.
- **Queue:** while a turn runs, the composer stays usable: messages from other threads queue, and their composer button reads **Queue** (with a clock icon). If the agent cannot steer, messages from the active thread queue too. Queued messages are listed above the composer of the thread they were written in, the next one to run at the bottom (as in the Queue tab), each with Edit (in place) and Remove, and run in that thread. When a turn ends normally (`end_turn`) or is cancelled, the next queued message is sent straight away. A failed or cut-short turn pauses the queue: the composer and status line show "paused" with **Resume**, and a message sent while paused and idle goes out right away; the queue moves on again after the next turn that ends normally. Removing the last queued message clears the pause. The queue is kept by the main process in memory, so it works for sessions that aren't open but is lost when Gloss quits. Works with any agent (no steering).
- **Steer:** while a turn runs, the active thread's composer button reads **Steer**, and it, Enter and `Ctrl+Enter` inject the message into the running turn instead of queueing it ("skip the tests"). There is no way to queue it instead. Steering is used only when the agent advertises it; otherwise messages queue: the Claude adapter's `_session/steering` extension (`_meta.steering.supported` in `initialize`). Gloss records the message first (marked "steered" in the log) so the agent's answer lands below it, then sends it with `idleBehavior: "promptRequired"`; if the turn ended before it got in, the message is taken back and goes to the front of the queue. Other threads can only queue while a turn runs, so the reply stays in the thread it belongs to.
- **Send to main:** a thread's composer (once the thread exists) also has **Send to main**, in its **…** menu beside the send button, which sends its text and attachments to the main conversation instead, tagged as continuing that thread (see Wire format). `Ctrl+Shift+Enter` (`Cmd+Shift+Enter` on macOS) does the same, including inside code blocks. The menu item shows only Send to main; its hover tooltip includes the shortcut. It is a main-thread message: it steers when the main conversation is active and steering is supported, queues when another thread is active, and shows in the main conversation. The menu item remains **Send to main**. The side panel stays on the thread. Each sent message leaves a Sent to main marker in the source thread at its place in the log, with a short text or attachment preview and an action to reveal the actual message in the main conversation. These are display references derived from saved routing tags, including for older sessions, not duplicate messages sent to the agent.
- **Attachments:** paste or drop images and files on the composer, or pick them with **+**. Images become ACP `image` blocks; text files become embedded `resource` blocks (with a `file://` URI when the file has a path). Only what the agent's `promptCapabilities` allow (`image`, `embeddedContext`); the **+** button and drops are off otherwise. Limits: images 10 MB, files 1 MB and text only. Attachments show as thumbnails or names in the composer and in the sent message. The **+** button (a paperclip) opens a small menu: **Attachments** (the file picker) and **Screen capture** (see Visual feedback), disabled with the reason when the agent takes no images.
- **Markdown editor:** the composer's text box is a CodeMirror 6 markdown editor (`@codemirror/lang-markdown`, GFM). The source stays visible and is styled: bold, italics, headings, inline code, links, quotes, with markup characters faded. What the user sees is exactly what the agent receives. Affordances:
  - Enter sends (steering the active thread when supported, otherwise queueing during a turn), except inside a ``` code block (open, or before its closing fence), where it adds a line. `Ctrl+Enter` sends with the same routing, including inside code blocks.
  - Shift+Enter adds a line; in a list or quote it continues the markup: `-`, `*`, `1.` (renumbering the items after it) and `- [ ]`. On an empty item it ends the list. Backspace right after a list marker or `>` removes it.
  - Tab nests the cursor's list item under the one before it (at that item's text column), Shift+Tab moves it out to its parent's level, with its lines and sub-items. Outside a list, Tab indents the cursor's line (or every selected line) by two spaces and Shift+Tab removes up to two, so Tab doesn't move focus out of the composer.
  - `Ctrl+B` bold, `Ctrl+I` italic, `Ctrl+E` inline code: wrap the selection, unwrap it when already wrapped, or insert a pair around the cursor. `Ctrl+K` makes the selection a link with the URL selected. Pasting a URL over selected text makes it a link.
  - Undo and redo (`Ctrl+Z`, `Ctrl+Shift+Z` / `Ctrl+Y`) cover all of these.
  - The slash command menu, pasted and dropped attachments, and drafts work as before. The editor grows to 8 lines, then scrolls. Editing a queued message stays a plain text box.
- **Sent messages** render through the same markdown renderer as the agent's replies (no raw HTML, safe links only, highlighted code), with each newline kept as a line break.
- **Context mentions:** type `@` at a word boundary for file and folder completion relative to the session directory, `@diff` for unstaged changes, `@staged` for staged changes, `@chat:` for another conversation's transcript, or `@terminal` for the last shell command and output. The selected completion scrolls into view as Up/Down moves it, and mouse movement changes selection. Selecting a file reads a snapshot into a visible attachment chip, removes the typed mention, and never sends the message. A Downloads shortcut browses the OS Downloads directory. Explicit absolute paths, `@~/Downloads/` and `@../` browse directories outside the project one level at a time; selecting a directory continues completion. Quoted mentions such as `@"C:/My Files/` support spaces. Git projects respect ignore rules in suggestions; non-Git folders use a bounded file scan. Project-relative file references cannot silently follow symlinks outside the project; explicitly selected absolute files may be outside it. Text files are limited to 1 MB; folder bundles to 50 UTF-8 text files and 1 MB total, with an explicit error rather than partial attachment. Images use the existing attachment formats and 10 MB limit. Context requires the agent's corresponding attachment capability.
- **Shell mode:** start a prompt with `!` to run a command directly in the session directory, using PowerShell on Windows and the user's shell on Unix. The input takes the conversation code block styling (background, inset and monospace text), without the helper caption, and the button reads Run command; no agent turn starts. While it runs, Escape cancels the process tree. Commands are noninteractive, have a five-minute limit, and capture up to 900 KB of combined stdout/stderr. Shift+Enter inserts a literal newline without Markdown list continuation; Enter runs the complete command, preserving internal line breaks as one shell script. Submitting clears the command input immediately and leaves the composer available for another message while the command runs. Completion leaves no shell-result panel, output attachment or inserted draft text. In-flight commands survive switching composers, and the last result stays in memory for explicit retrieval while Gloss runs. `@terminal` can explicitly attach the most recent result in the session when requested.
- **Conversation rewind:** Double Escape (two separate presses within 400 ms) clears a nonempty composer first, including attachments, preserving the cleared draft in the Ctrl/Cmd+S stash. With an empty composer, Double Escape or `/rewind` opens a keyboard-first menu listing the session's user messages, newest first. Up/Down browses, Enter or clicking a point immediately triggers removal of that message and all later messages, tools and plans across threads. Threads anchored to removed messages are removed too; newer standalone review threads are removed when their timestamps place them after the rewind point. Rewind refuses active turns and nonempty queues. It never changes project files. Escape closes the list. The first Escape cancels the active session turn (or this composer's shell command); completion menus get first priority. Holding Escape does not trigger rewind, and another key or a menu dismissal resets the double-tap sequence. The shortcut also works while reading the log.
- **Native rewind only:** rewind continues from the agent's own history: the agent forks its saved session just before the selected message, keeping every earlier user, assistant and tool record, images, thinking and tool results included, and Gloss switches the conversation to the fork. Retained history is never flattened into a prompt or resent, and Gloss puts no size limit on it (the agent's context limits and compaction still apply). Only Claude Code and Codex support it, through their adapters' message-targeted `session/fork` (`_meta.jetbrains.air.fork`, not standard ACP: plain `session/fork` copies the whole session, so support is per agent, not per capability). Other agents offer no rewind: `/rewind` isn't listed, and Double Escape on an empty composer shows a note, "<Agent> doesn't support rewind.", that fades after a few seconds. There is no transcript-reconstruction fallback.
- **Rewind boundary:** Claude's cut point comes from its transcript: the user or assistant entry the selected message follows, which keeps a cancelled turn's tool result and interrupt marker and reaches past a compaction (rewinding there restores the uncompacted history). Codex forks whole turns, so Gloss names an item of the turn before (its last agent message, else its prompt). Steered messages aren't rewind points: they belong to their turn. User messages sent live have no agent id until a replay gives them one, so a rewind may first replay the session (cheap for Claude, which keeps its process). Rewinding to the first message starts a new agent session. If the agent can't fork (an id it can't find, an error), the rewind fails with that error and nothing changes; it never falls back to copying the whole history.
- **After a rewind:** the log changes only once the fork exists. The fork's id is saved as the session's agent session, and the next attach loads it; its replay keeps the retained entries' ids, pins and thread anchors and gives retained user messages the fork's ids. If loading fails, the fork stays saved and the next send or retry loads it again, across restart too. The old agent session is kept by the agent but hidden from Gloss's import list; there is no redo. Conversations an older Gloss rewound by resending a transcript keep that history: a transcript not sent yet is still sent with the next prompt, and rewind there is offered only after the message that carried it.
- **Local slash actions:** `/stash`, `/editor` and `/rewind` (for agents that support rewind) expose those composer actions alongside the agent's advertised commands. An agent command with the same name takes precedence. Local actions run in Gloss without starting an agent turn. The composer has no extra action-button row; its shortcuts are listed in Settings.
- **History:** Up in an empty composer replaces its text with the previous message the user sent and starts cycling: from then on Up shows the previous message and Down the next, whatever line the caret is on, with the caret at the end of each; at the oldest, Up does nothing. Down past the newest empties the composer again and stops cycling. Once anything is typed, Up and Down only move the caret. Editing the text or moving the caret (a click, Left, Right, Home, End, even where the caret can't move) also stops it: the user is now working on that message, so Up and Down move between its lines until it is sent or the composer is cleared. Every composer shares one history: the user's messages from every session and thread, newest first, each text once (at its latest use), from the DB so it survives restarts (`history()`, at most 500). Text only: attachments aren't recalled. A recalled `/command` doesn't open the slash menu.
- **Drafts:** each composer (a session's main thread, or one thread anchor) keeps its unsent text, attachments and caret position when the user switches to another session or thread and back. Drafts are kept in the renderer's memory, so they are lost when Gloss quits.

## Visual feedback

Pointing at things on screen to give the agent feedback (`docs/mocks/visual-feedback.html`): capture part of the screen, mark it up with numbered pins and drawings, send it, and discuss each pin in its own thread.

- **Starting:** **Screen capture** in the composer's **+** menu (its tooltip names the current shortcut, "Screen capture (Ctrl+Shift+PrtSc)"), or the **capture shortcut**, the only one, which works the same whether Gloss or another app is in front: the `captureShortcut` setting, `Ctrl+Shift+PrintScreen` by default, empty for none. It is registered with `globalShortcut`, so other apps lose those keys while Gloss runs (which is why the default isn't `Ctrl+Shift+S`, Save As almost everywhere). Either goes to the composer used last (else the one shown). The menu item is disabled, saying "This agent doesn't accept images.", when the session's agent doesn't advertise `promptCapabilities.image`. Gloss doesn't hide: it is part of what can be captured. Started from another app, the overlay takes the keyboard focus (Windows refuses `SetForegroundWindow` to a background program, so Gloss attaches its input thread to the foreground window's for the call) and Gloss comes to the front with the canvas once something is picked.
- **Region overlay** (ShareX's region capture, with its defaults): the main process freezes every display (`desktopCapturer`, each in its own pixels; it scales every screen to one size per call, so it is called once per display size) and covers each with a frameless always-on-top window showing its frozen copy. The display with the cursor is dimmed 20% except the area that would be captured, which has a 1 px accent outline with black marching ants; the others are dimmed whole until the cursor comes onto them, which also gives that overlay the keys. A region stays on one display; a window across two is captured on the display clicked. Any overlay's Esc or right-click cancels them all.
  - Hovering highlights the window under the cursor and a click captures it; over the desktop a click takes the whole display. Window frames come from Windows (`EnumWindows`-order `GetTopWindow`/`GetWindow`, DWM's extended frame bounds; invisible, minimized, cloaked and click-through windows skipped, ones hidden entirely under others dropped) through `koffi`. Other platforms have no window list: a region or the whole display.
  - Dragging draws a region (Shift: a square) with its size at its corner and a crosshair at its center; releasing captures it (regions under 5 px are dropped). Space captures the whole display under the cursor. Right-click drops the region being drawn, or cancels; Esc cancels. Arrow keys nudge the cursor 1 px (Shift: 10).
  - A magnifier beside the cursor shows 15 × 15 pixels at 10×, the center pixel outlined, with the cursor's X and Y under it. A hint at the top ("Drag a region · Click a window · Space whole display · Esc cancel") fades once a drag starts.
  - The overlay is its own page with its own preload, which can only read the frozen frame and say what was picked; the main process crops the PNG. Only the Gloss window can start a capture, one at a time.
- **Annotation canvas:** a dialog filling the Gloss window below the title bar (so its close button never sits under the window controls). A capture opens fitted and centered (never enlarged); resizing the window afterwards keeps the view. Zoom (5% to 800%) with the wheel, at the cursor, or the toolbar's − and +; the zoom button shows the percentage and switches between fit (`0`) and actual size (`1`). There are no `+`/`-` keys (they read as text sizing). From 200% pixels are drawn sharp. Pan by dragging with the right button anywhere, or the left button on the background around the capture; panning isn't held at the stage's edges (`0` brings the capture back). The pins column hides from a button on its own header and then shows as a rail like the threads panel's (a pin icon with the count; clicking it brings the column back) and resizes by its edge (220 to 560 px); both are remembered in localStorage. Tools: **Pen** (`F`, selected when the dialog opens), **Highlighter** (`H`), **Box** (`R`), **Arrow** (`A`), **Pin** (`N`), five colors for marks, undo and redo (`Ctrl+Z`, `Ctrl+Y`). Pins are numbered in order and always Gloss pink, so they read as anchors; placing one puts the caret in its note when the pins column is open (a closed column stays closed, so it doesn't cover the pin); clicking one with any tool opens the column if needed and puts the caret in its note; dragging one with the Pin tool moves it; deleting one renumbers the rest. The pins column lists the pins with their notes. **Retake** reopens the overlay; **Add to message** (`Ctrl+Enter`) flattens marks and pins into the image and adds it to the composer; Esc cancels. The last color is kept while Gloss runs. With an empty pin note focused, `Ctrl+Z` undoes the last annotation; nonempty notes keep native text undo.
- **In the composer:** the capture is an image attachment with a pin count; hovering shows **Edit**, which reopens the canvas with its pins and marks until the message is sent. Hovering an attached image (pasted, dropped or picked) also shows **Edit**: it opens the canvas on that image, without Retake, and adding replaces the image with the annotated one under its own name. The flattened image is a PNG, or a JPEG when the PNG would pass the API's 5 MB image limit.
- **Sending:** the image goes as an ACP `image` block and its pins as text after the message's text (see Wire format), so the agent can refer to them by number (Set-of-Mark prompting). Pins are stored on the attachment (`pins`), so they survive restarts and syncs.
- **Pins are anchors:** the sent message shows the screenshot (up to 420 px high) with each pin as a target, and the notes listed under it. Clicking a pin or its note opens its thread; a pin with a thread carries its reply count (a running dot while its turn runs) and the pin whose thread the panel shows is ringed. Clicking the image enlarges it, pins still clickable. The thread's quote is the screenshot around the pin (a 120 × 72 window at half size) with its note, its composer reads "Reply about pin 2", and its name elsewhere is "Pin 2: <note>". **Find in main** scrolls to the pin.

## Obsidian project shortcut

The project section of Settings includes **Obsidian vault**, saved as `projects[folder].obsidianVault`. Enter an existing vault's name or ID. Empty or whitespace hides the shortcut. Changes apply live and each project keeps its own vault.

An **Obsidian** logo button (with a vault tooltip and accessible label) appears immediately after the project folder button in both conversation and review status lines. It opens or focuses the configured vault using Obsidian's built-in `obsidian://open?vault=...` protocol. The main process resolves the vault from the session's project settings and encodes its name as a single parameter. Launch failures appear in the status line. Obsidian must be installed and the vault already registered there.

## Status line

Opening a status line menu closes any other open menu. Clicking outside or pressing Escape closes it.

A line under the composer for the open session (in a review, a band under the diff). Each item is a 24px pill with an icon or a faint label before its value, and a tooltip saying what it is; the ones that open a picker or panel end in a chevron. The agent's items come first and never wrap: those that don't fit are hidden, right to left. The folder, branch, pull request and Obsidian sit at the right end, and the folder and branch names shorten with an ellipsis. Agent state comes from ACP; the usage popup asks Claude Code or Codex directly, and git details come from local commands:

- "Agent not running" when the session isn't resumed and no turn runs (whether and where the agent works is the activity strip's, and the log's)
- queued messages: "2 queued" (yellow; only where no activity strip shows it, i.e. in a review), or "2 queued, paused · Resume" (purple; clicking resumes)
- context use: "Context", a meter and "4% of 1M", from `usage_update` `used`/`size` (amber from 80%)
- session cost, from `usage_update` `cost`, e.g. "$0.01"
- plan usage limits, Claude Code only: the Claude adapter attaches Claude Code's rate-limit info to `usage_update` as `_meta["_claude/rateLimit"]` (`rateLimitType`, `status`, optional `utilization`, `resetsAt` in Unix seconds), one window per update. Gloss keeps the latest per window and shows non-weekly windows: "5h limit OK" (Claude Code reports no percentage far from the limit), "5h limit 82%" (amber when warned), or "5h limit reached · resets 3:40 PM" (red when reached). Weekly limits stay in the usage popup and never appear in the status line. The tooltip has the reset time. Agents that don't send it show nothing.
- **Usage popup:** clicking any usage item (context, cost or plan limit) for Claude opens a popup; before usage arrives, a "Usage" button opens it. It shows the current session's context window, then the account's plan, session and weekly limits, per-model limits when reported, and extra usage when enabled. Limits have bars, percentages and reset intervals. The main process asks a short-lived Claude Agent SDK query for `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET({ skipBehaviors: true })`, with no prompt and `persistSession: false`, then closes it. Nothing is added to the conversation or session list, and it works while a turn runs or the allowance is exhausted. Successful results are cached for 30 seconds and concurrent requests share the fetch; fetching times out after 15 seconds. Loading, unavailable limits and errors appear inside the popup, with retry after errors. Escape, an outside click or changing sessions closes it. Context comes from the current session's ACP usage, never the temporary query. The experimental SDK dependency is pinned.
- **Codex usage popup:** the same usage items (or the initial "Usage" button) open the popup for Codex. A short-lived bundled `codex app-server` performs the initialization handshake, reads `account/read`, then `account/rateLimits/read` for subscription accounts, and closes stdin. No thread or turn is created. It displays the account's reported quota windows, named buckets, used percentages and reset times, with context from the real session. API key accounts show unavailable plan limits. Cache and concurrent requests are separate per agent, with the same 30-second freshness, 15-second timeout, loading, retry and dismissal behavior as Claude.
- model: the agent's config option with category `model`, shown by name, except that a `default` option shows its description, which names the model it stands for (Claude Code's "Default (recommended)" shows as e.g. "Opus 5.5"); clicking opens a picker that calls `session/set_config_option`. The choice is saved on the session and re-applied when it is resumed.
- effort, right after the model: the agent's config option with category `thought_level` (Claude Code's "Effort", Codex's "Reasoning effort"), shown by name, e.g. "High" (its tooltip says "Effort"); clicking opens a picker that calls `session/set_config_option`. Its levels depend on the model, and it is hidden when the model has none. Saved on the session and re-applied on resume after the model, when the model offers it. Gloss always shows a real level: when Claude's adapter reports `default` (nothing picked here or in Claude Code's settings), Gloss sets the level the adapter itself recommends (`medium`, else the model's first level), and again after a model switch puts it back on `default`; the picker doesn't offer "Default". Gloss doesn't use the adapter's own way of doing this (the JetBrains AIR `recommendedValue` client capability), because claiming to be an AIR client changes how the adapter sends updates, plans and tool calls.
- "Waiting for you" (amber, a hand icon) while the agent waits on a question or approval (see Questions and approvals)
- permission mode: a shield and the current mode's name, e.g. "Bypass permissions" or "Manual"; clicking opens a picker of the agent's modes (see Permission modes). For an agent without a bypass mode the picker also has "Approve requests automatically"; while it is on the item is amber and adds "· auto-approve". An agent with no modes shows "Auto-approve" or "Ask".
- **Extensions** (a puzzle icon): what the agent loaded, from its commands: commands and skills, and MCP prompts (`mcp:<server>:<prompt>`). When the agent has an `/mcp` command, "Show MCP server status" sends it in the main thread (Claude Code answers with each server's status). Codex adapter MCP startup diagnostics (`mcp_startup.*` tool IDs) are excluded from the conversation during live turns and replay; previously cached reports are removed on database upgrade. Actual MCP tool calls and explicitly requested `/mcp` responses remain visible. Use `/mcp` for connection status or `/mcp reconnect` in Codex to retry and inspect startup failures. Gloss doesn't install or configure extensions.
- the git branch of the session folder with `*` when the tree is dirty (`git status --porcelain --branch` in the main process; hidden outside a repo; refreshed when a session opens and after each turn). When the branch's upstream is on GitHub, clicking it opens the branch there.
- the branch's GitHub pull request, from `gh pr view` in the main process with the user's own `gh` login: "#12 open" colored by state (open, draft, merged, closed), a dot for the combined checks (passing, failing, running) and a tooltip with the title and review decision. Clicking opens it in the browser. Hidden without `gh`, its login, a GitHub remote or a PR. A merged or closed PR shows only while the branch is still at its last commit, so a long-lived branch drops it once new work starts. Refreshed with the branch (the last result per folder and branch shows meanwhile), and every 90 s while its checks run and the window is focused.
- the session folder; clicking opens it in the system file manager (`shell.openPath` in the main process, which looks the folder up by session id rather than taking a path from the renderer)

## Keyboard shortcuts

`Ctrl+W` closes the current session view and returns to the previous view, keeping its history and sidebar entry. In a separate session window it closes that window. Held keys do not repeatedly close views. On macOS, use Cmd.

In a session (including its own window), `Ctrl+Alt+E` opens its folder in File Explorer (Finder on macOS), `Ctrl+Alt+B` opens its branch on GitHub, `Ctrl+Alt+P` opens its pull request, and `Ctrl+Alt+O` opens the configured project Obsidian vault. Branch, PR and vault actions apply only when their status bar controls are available. The controls show the shortcuts in their tooltips. Held keys do not repeatedly open windows. On macOS, use Cmd+Option for Ctrl+Alt.

`Ctrl+Shift+F` search conversations · `Ctrl+N` new session · `Ctrl+Shift+D` review the branch's changes with the default agent, or leave the open review · `Ctrl+Tab` / `Ctrl+Shift+Tab` next / previous session in the project · `Ctrl+L` focus the composer · `Ctrl+Shift+T` show or hide the side panel · `Ctrl+J` go to where the agent is working, or last worked (the thread of the latest message sent), with the caret in that composer (the main conversation's when it was there; nothing in a session without messages) · `Ctrl+Shift+Q` show the queue · the capture shortcut (`Ctrl+Shift+PrintScreen` by default, a setting; see Visual feedback for the overlay's and canvas's keys) · `Ctrl+Shift+H` show or hide comment cards and `N` / `P` next / previous open thread (review sessions) · `Ctrl+Shift+O` pop the session out into its own window, or return it to the main window (see Session windows, which also says which shortcuts work there) · `Esc` close settings or a menu, or cancel the turn from the working thread's composer · `Ctrl+,` settings. `Cmd` works for `Ctrl` on macOS. The mouse's back and forward buttons, and `Alt+Left` / `Alt+Right`, move through the views visited: a session with its open thread (or none), and the settings screen. Deleted sessions are skipped. On macOS, `Option+arrow` in a text field still moves by word. On a focused question or approval card, `1` to `9` pick, `Enter` submits or allows once, and `Esc` declines or rejects once (see Questions and approvals). The settings screen lists these and the shortcuts that apply in one place (composer, queued messages, selections, session list, panel edges, question and approval cards); they can't be changed, except the capture shortcut, which is a setting.

## Notifications

When a turn ends or fails while no Gloss window is focused, Gloss shows an OS notification (session title; "The agent finished", "The agent replied in a thread" or the error). Cancelled turns don't notify, and neither does a turn whose queued follow-up starts straight away. Clicking it focuses the window holding the session (its own window when popped out, else the main one) and opens the session and thread. Tool completion, turn completion and history sync never focus the window, change the selected session or thread, close Settings, or move the caret. On Windows the taskbar button does not flash. The taskbar icon carries a small badge (a plain 8 px overlay dot in the in-app state colors, with transparent padding and no white ring): red while a session has an unseen failure, else green while one has an unseen finish (the sidebar's red and green dots), else blue while any turn runs, else none. It clears once every finished session has been looked at. Where the OS has a dock badge (macOS, some Linux docks) it counts the unseen sessions instead. Windows needs an AppUserModelID for notifications to show.

The same finishes (not cancelled, no queued follow-up) play a short chime, synthesized with Web Audio, when the window isn't focused or the session isn't the open one. The notification itself is silent, so the system's sound doesn't double it. The **Sound when a turn finishes** setting (on by default) turns the chime off.

While any turn runs, Gloss keeps the computer from going to sleep (Electron's `powerSaveBlocker`, `prevent-app-suspension`; the display may still turn off). It lets go once no turn is running.

### Composer attachment and rewind layout

The approved treatment is option B in `docs/mocks/composer-review.html`. Draft text appears before attached context. Images form a horizontal compact strip, each with a contained preview at its natural aspect ratio, a filename, pin count, and adjacent Annotate and Remove actions. Controls never overlap the image. Clicking a preview opens the full image, and file chips form a separate row below the text and image strip. Attachment indices retain their original send order even though the display groups images and files. The empty composer keeps its single-row controls.

The rewind picker follows the approved mock: a simple titled header, a scrollable list of sent prompts with timestamps and later-message counts, a subtle selected row with an accent marker, without a subtitle, close control, or footer. Selecting a message immediately rewinds without a confirmation screen. Files stay unchanged. Escape and keyboard navigation retain their existing behavior.

Sent image attachments render as standalone previews below the user message bubble, including annotated screenshots and their pin notes. Image-only messages have no empty bubble. Previews preserve aspect ratios and open the existing enlarged view; pin replies keep their original attachment indices.

After a successful rewind, the selected message's full text and attachments populate the main session composer for editing and resending. This also works when rewind closes a thread panel. Existing draft content is stashed, and a failed rewind does not replace the draft.

Entering rewind when the latest user message belongs to a cancelled turn automatically rewinds to that message and restores its draft. If cancellation is still pending, rewind waits for the turn to end before checking. Otherwise it opens the normal message picker. Automatic-rewind failures show an error and allow manual selection.

Automatic rewind after cancellation displays no loading or rewinding modal. Cancellation reports its outcome without waiting for agent session-list bookkeeping. The rewind returns once the agent has forked; loading the fork waits for the next prompt, and a failed load leaves the fork to retry, including across restart.
